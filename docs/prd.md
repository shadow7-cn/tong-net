# 同网互通 PRD

## 问题背景

用户需要一个免费、公益、无需账号、无需云服务的局域网互通工具。在同一个局域网内，一台 Windows 或 macOS 电脑开启桌面端服务后，手机、平板、其他电脑可以通过浏览器扫码或复制局域网地址访问，并完成文件传输和简单聊天。

现有替代方案各有摩擦：网盘需要登录和公网传输，聊天软件的文件助手不适合多设备临时互传，U 盘和数据线不够方便，AirDrop 等能力又受生态限制。同网互通要解决的是“同一网络下临时互传东西和沟通”的低心智负担场景。

## 方案概述

同网互通提供一个 Tauri 桌面应用作为局域网主机。用户点击按钮开启服务后，应用展示局域网访问地址和二维码。其他设备通过浏览器进入 Web 客户端，设置设备昵称，并在设备列表中打开对应设备的一对一会话。

第一版采用主机中转模型，而不是浏览器之间的 P2P 直连。用户体验上像是设备 A 直接把文件或消息发给设备 B；底层实现上，所有消息、文件和记录都经过开启服务的主机统一管理。

文件传输第一版采用务实策略：上传不支持断点续传，上传中断后任务失败并清理临时文件；下载支持 HTTP Range 断点续传。这样可以让第一版保持稳定，同时保留大文件下载体验。

## 用户故事

1. 作为桌面端用户，我希望点击一个按钮就能开启局域网服务，这样附近设备不需要配置就能连接。
2. 作为桌面端用户，我希望可以在应用里停止局域网服务，这样我能立刻关闭访问入口。
3. 作为桌面端用户，我希望看到当前局域网访问地址，这样我可以复制给其他设备。
4. 作为桌面端用户，我希望看到二维码，这样手机扫码就能快速进入。
5. 作为桌面端用户，我希望看到服务是否正在运行，这样我知道其他设备现在能不能连。
6. 作为桌面端用户，我希望看到当前已连接设备，这样我知道谁正在使用这个服务。
7. 作为浏览器端用户，我希望不用安装软件，直接打开局域网地址就能使用，这样手机、平板、其他电脑都能进来。
8. 作为浏览器端用户，我希望可以扫码进入 Web 页面，这样手机端接入更快。
9. 作为浏览器端用户，我希望设置自己的设备昵称，这样其他设备能认出我是谁。
10. 作为浏览器端用户，我希望昵称能保存在浏览器里，这样刷新页面后不用重复设置。
11. 作为浏览器端用户，我希望每个浏览器都有稳定的设备身份，这样历史会话能对应到正确设备。
12. 作为用户，我希望看到在线设备和历史设备列表，这样我能选择要和谁沟通。
13. 作为用户，我希望离线设备仍然保留在历史里，这样过去的聊天和文件记录不会丢。
14. 作为用户，我希望打开某个设备的一对一会话，这样消息和文件能按接收对象整理。
15. 作为用户，我希望开启服务的主机电脑也显示为一个设备，这样手机可以直接把文件发给本机。
16. 作为用户，我希望在设备会话里发送文字消息，这样局域网内可以简单沟通。
17. 作为用户，我希望消息接近实时到达，这样聊天体验是顺畅的。
18. 作为用户，我希望看到设备加入、离开、文件发送等系统消息，这样我知道当前发生了什么。
19. 作为用户，我希望在设备会话里发送文件，这样文件传输和聊天使用同一个操作入口。
20. 作为发送方，我希望可以从浏览器选择一个或多个文件，这样我能把本机文件传给另一个设备。
21. 作为发送方，我希望看到上传进度，这样我知道文件是否还在传输。
22. 作为发送方，我希望上传失败能明确显示，这样我知道需要重新上传。
23. 作为发送方，我希望上传中断后任务失败并自动清理临时文件，这样不完整文件不会被误认为传输成功。
24. 作为接收方，我希望收到的文件以文件卡片显示在会话里，这样我可以决定是否下载。
25. 作为接收方，我希望手动点击下载文件，这样文件不会在我不知情的情况下保存。
26. 作为接收方，我希望下载支持断点续传，这样大文件下载中断后可以继续。
27. 作为桌面端用户，我希望上传成功的文件保存到指定目录，这样之后能找得到。
28. 作为桌面端用户，我希望临时上传文件和最终文件分开保存，这样失败上传不会污染正式文件列表。
29. 作为桌面端用户，我希望传输记录保存在本地，这样之后可以查看收发过哪些文件。
30. 作为桌面端用户，我希望聊天记录保存在本地，这样应用重启后历史还在。
31. 作为用户，我希望设备断开后文件消息仍然保留在历史里，这样完成的传输还能被查看。
32. 作为用户，我希望局域网访问地址带有会话访问令牌，这样同一网络里的陌生设备不能随便进入。
33. 作为桌面端用户，我希望每次开启服务时生成新的访问令牌，这样旧链接不会长期有效。
34. 作为桌面端用户，我希望应用明确提示只在可信局域网使用，这样我清楚它的安全边界。
35. 作为桌面端用户，我希望可以设置端口、保存目录和本机设备名，这样能适配我的使用习惯。
36. 作为用户，我希望界面简单、实用、偏工具化，这样它像一个可靠的传输工具，而不是复杂社交软件。

## 实现决策

- 桌面端使用 Tauri 构建，目标平台是 Windows 和 macOS。
- 桌面端负责服务生命周期：开启、停止、当前状态、局域网地址、二维码、连接设备、设置项和本地历史。
- 使用本地 HTTP 服务承载浏览器页面和 REST API。
- 使用 WebSocket 处理实时设备在线状态、聊天消息、文件事件和传输进度通知。
- 第一版采用主机中转模式。所有浏览器客户端都通过开启服务的桌面主机通信。
- 第一版不做浏览器之间的 P2P 直连。
- 把开启服务的主机电脑也建模成一个普通设备，由桌面端用户命名。
- 每个浏览器客户端分配一个 `deviceId`，并保存在浏览器本地存储里。
- 允许用户设置设备昵称，并在浏览器本地持久化。
- 设备之间采用一对一会话作为主要交互模型。
- 消息记录包含发送设备、接收设备、消息类型、时间戳，以及可选的文件引用。
- 文件传输在产品上表现为会话里的文件消息。
- 上传文件先写入临时文件，上传完整成功后再原子移动到最终保存位置。
- 如果上传请求中断或失败，任务标记为失败，并删除对应临时文件。
- 第一版不支持上传断点续传。
- 下载支持 HTTP Range，并返回 `206 Partial Content`，用于实现下载断点续传。
- 本地持久化保存传输记录、聊天记录、设备、会话和文件记录。
- 默认按会话参与者限制文件可见性。A 发给 B 的文件，C 默认看不到。
- 浏览器访问地址和 API 请求使用会话访问令牌做基础访问控制。
- 除非未来用户主动选择持久模式，否则每次开启局域网服务时生成新的访问令牌。
- 产品定位是免费公益软件，默认不需要账号、不做云同步、不采集用户数据。

## 测试决策

- 测试优先覆盖外部可见行为，不优先测内部工具函数。服务端 API 和 WebSocket 行为应该从调用边界验证。
- 测试桌面端服务生命周期：开启服务后浏览器页面和 API 可访问；停止服务后新访问被拒绝。
- 测试访问控制：缺少令牌或令牌错误时，HTTP 和 WebSocket 都应该拒绝访问。
- 测试设备注册：浏览器第一次访问会创建设备身份；带着已保存身份再次访问时仍是同一个设备。
- 测试一对一消息路由：发给设备 B 的消息只投递给 A 和 B，不投递给无关设备 C。
- 测试文件上传成功：完整上传后生成最终文件记录，并在会话里生成文件消息。
- 测试文件上传失败：中断上传不会留下最终文件，并且会清理临时数据。
- 测试下载 Range：合法范围请求返回 `206 Partial Content`，并且返回正确的字节内容。
- 测试持久化：服务重启后，已完成消息、设备、会话和文件记录仍然可用。
- 前端完成后，用浏览器自动化测试核心流程：开启服务、打开 Web 页面、修改昵称、发送消息、上传文件、下载文件。

## 暂不包含

- 上传断点续传。
- 浏览器之间的 P2P 直连传输。
- 群聊或广播会话。
- 公网访问、NAT 穿透或中继服务器。
- 用户账号、登录、云同步或远程备份。
- 手机原生 App。
- 复杂的主机共享目录浏览。
- 收到文件后自动下载。
- 浏览器客户端之间的端到端加密。
- 多个桌面主机之间的联邦互联或自动发现。
- 超出基础会话令牌之外的复杂权限角色。

## 补充说明

第一版应该优先追求清晰和可靠。产品应该像一个带聊天界面的本地传输站，而不是完整社交软件。

第一版最重要的产品承诺是：打开桌面 App，开启服务，扫码进入，选择设备，发送文字或文件，并在本地保留记录。下载断点续传值得第一版支持，因为它基于标准 HTTP 能力，对大文件很有价值。上传断点续传先不做，因为它会引入分片协议、文件指纹、恢复状态和大量边界情况，会明显拖慢第一版。

未来版本可以在主机中转模型稳定后，再考虑上传断点续传、群聊、选择性共享目录、更细的设备权限，以及可选的 P2P 实验。
